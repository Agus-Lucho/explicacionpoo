📋 Introducción al Sistema

Este es un Sistema de Gestión de Cursos desarrollado en Java con interfaz gráfica Swing. Permite a alumnos inscribirse en cursos, realizar pagos, y ver sus calificaciones. Los docentes pueden crear cursos, calificar alumnos y ver información de estudiantes.

🎯 Objetivo

Sistema educativo completo con gestión de usuarios, cursos, inscripciones y pagos

🛠️ Tecnologías

Java, Swing (GUI), JSON (persistencia), POO avanzada

🏗️ Arquitectura del Sistema

1️⃣ Inicio de la Aplicación

🚀 Main.main() - Punto de Entrada
public static void main(String[] args) { SwingUtilities.invokeLater(() -> new VentanaPrincipal()); }

¿Qué pasa aquí?

  • SwingUtilities.invokeLater() ejecuta el código en el Event Dispatch Thread (EDT)
  • ¿Por qué? Swing NO es thread-safe. Todas las operaciones de UI deben ejecutarse en el EDT para evitar problemas de concurrencia
  • Se crea una instancia de VentanaPrincipal
  • Esta es una expresión lambda que equivale a crear un Runnable
🏗️ Constructor VentanaPrincipal()
public VentanaPrincipal() { setTitle("Plataforma de Cursos"); setSize(700, 500); setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE); setLocationRelativeTo(null); setLayout(new BorderLayout()); GestorArchivos.inicializarDatos(); // ¡CRUCIAL! crearPanelInicio(); crearPanelRegistro(); crearPanelLogin(); add(panelInicio); setVisible(true); }

Paso a paso:

  1. Configuración de ventana:
    • Título, tamaño 700x500px
    • EXIT_ON_CLOSE: cierra la app al cerrar ventana
    • setLocationRelativeTo(null): centra en pantalla
    • BorderLayout: gestor de diseño principal
  2. 🔥 GestorArchivos.inicializarDatos(): Carga TODOS los datos desde archivos JSON (usuarios, cursos, inscripciones, calificaciones)
  3. Creación de paneles: Crea 3 paneles (inicio, registro, login) pero solo muestra el de inicio
  4. setVisible(true): Muestra la ventana al usuario
💾 GestorArchivos.inicializarDatos() - Carga de Datos

Esta es una de las funciones MÁS IMPORTANTES del sistema. Se ejecuta UNA VEZ al iniciar la app.

public static void inicializarDatos() { usuarios.clear(); usuarios.addAll(leerUsuarios()); cursos.clear(); cursos.addAll(leerCursos()); inscripciones.clear(); inscripciones.addAll(leerInscripciones()); calificaciones.clear(); calificaciones.addAll(leerCalificaciones()); reconstruirRelaciones(); // ¡CRÍTICO! }

Flujo de carga:

  1. Leer Usuarios: Lee usuarios.json, parsea cada línea JSON y crea objetos Alumno o Docente
  2. Leer Cursos: Lee cursos.json, busca el docente por ID y crea objetos Curso
  3. Leer Inscripciones: Lee inscripciones.json, crea objetos Inscripcion (sin referencias aún)
  4. Leer Calificaciones: Lee calificaciones.json, crea objetos Calificacion
  5. 🔥 reconstruirRelaciones(): Conecta todas las referencias entre objetos (alumno ↔ curso, docente ↔ curso, etc.)

⚠️ ¿Por qué reconstruirRelaciones()?

Los archivos JSON solo guardan IDs (alumnoId, cursoCodigo). Al cargar, necesitamos buscar los objetos reales en memoria y asignar las referencias. Esto reconstruye el grafo de objetos completo.

¿Qué hace guardarUnSoloUsuario()?

  1. Parsea el ID a int
  2. Crea un objeto Alumno o Docente según el tipo
  3. Agrega el usuario a la lista en memoria (usuarios)
  4. Guarda TODOS los usuarios en usuarios.json

💡 Concepto POO: Polimorfismo

Aunque guardamos en una lista de tipo Usuario, en runtime pueden ser Alumno o Docente. Esto es polimorfismo de subtipos.

🔢 Generación de IDs
public static String generarId(String tipo) { Random rand = new Random(); int num = rand.nextInt(9000) + 1000; // 1000-9999 return String.valueOf(num); }

Explicación:

  • nextInt(9000) genera números de 0 a 8999
  • Al sumar 1000, obtenemos rango 1000-9999 (4 dígitos)
  • ⚠️ Problema: No valida duplicados. Dos usuarios podrían tener el mismo ID
  • Solución correcta: Debería verificar en la lista usuarios antes de retornar

🐛 Bug potencial: Si se generan IDs duplicados, el login fallará o accederá al usuario incorrecto.

public static Usuario validarLogin(String nombre, String id, String tipo) { for (Usuario u : usuarios) { String usuarioIdString = String.valueOf(u.getId()); if (u.getNombre().equals(nombre) && usuarioIdString.equals(id) && u.getTipo().equalsIgnoreCase(tipo)) { return u; } } return null; }

  • Compara nombre, ID y tipo

Se usa instanceof para verificar el tipo real del objeto antes de hacer casting. Esto previene ClassCastException.

¿Qué es una clase de asociación?

Una clase de asociación representa una relación entre dos clases que tiene atributos propios.

  • Relaciona Alumno con Curso
  • Pero además tiene: fecha, estado, método de pago, monto, cuotas
  • No es solo una relación, es una entidad con identidad propia

Dos constructores - ¿Por qué?

  1. Constructor 1 (con objetos):
    • Se usa cuando se crea una NUEVA inscripción en runtime
    • Recibe objetos Alumno y Curso completos
    • Genera un ID nuevo con GestorArchivos.generarIdInscripcion()
    • Extrae los IDs de los objetos para persistencia
  2. Constructor 2 (con IDs):
    • Se usa cuando se CARGA desde JSON al iniciar la app
    • Solo tiene IDs, no objetos (alumno y curso son null)
    • Las referencias se reconstruyen después con reconstruirRelaciones()

Atributos duplicados (referencias + IDs):

private Alumno alumno; // Referencia al objeto private int alumnoId; // ID para persistencia private Curso curso; // Referencia al objeto private int cursoCodigo; // Código para persistencia

¿Por qué duplicar?

  • En memoria: Usamos las referencias (alumno, curso) para navegar el grafo de objetos
  • En JSON: Solo guardamos IDs porque no podemos serializar objetos completos (referencias circulares)
  • Al cargar, usamos los IDs para buscar los objetos y reconstruir las referencias

✅ Patrón: Separación de persistencia y lógica

Los IDs son solo para persistencia. En memoria trabajamos con objetos. Esto separa las preocupaciones de almacenamiento y lógica de negocio.

La clase padre define la estructura (atributos comunes) pero delega el comportamiento específico (cálculo) a las subclases. Esto es una forma del patrón Template Method.

  • Desventaja: No maneja casos edge (comillas escapadas, etc.)

Formato JSON esperado:

{"id":"1234","tipo":"alumno","nombre":"Juan","correo":"juan@mail.com","contrasena":"pass123","fechaRegistro":"2024-01-15"} {"id":"5678","tipo":"docente","nombre":"Maria","correo":"maria@mail.com","contrasena":"pass456","fechaRegistro":"2024-01-16"}

Cada línea es un objeto JSON. NO es un array JSON.

🔄 reconstruirRelaciones() - LA MAGIA

Esta es la función MÁS CRÍTICA del sistema:

private static void reconstruirRelaciones() { // 1. Limpiar listas en objetos for (Usuario u : usuarios) { if (u instanceof Alumno) { ((Alumno) u).getHistorialCursos().clear(); ((Alumno) u).getNotas().clear(); } else if (u instanceof Docente) { ((Docente) u).getCursosDictados().clear(); } } for (Curso c : cursos) { c.getInscriptos().clear(); c.getCalificacionesCurso().clear(); } // 2. Reconstruir relación Docente ↔ Curso for (Curso c : cursos) { if (c.getDocente() != null) { Optional<Docente> docenteEnMemoria = usuarios.stream() .filter(u -> u instanceof Docente && u.getId() == c.getDocente().getId()) .map(u -> (Docente) u) .findFirst(); docenteEnMemoria.ifPresent(d -> { if (!d.getCursosDictados().contains(c)) { d.dictarCurso(c); } }); } } // 3. Reconstruir Inscripciones for (Inscripcion insc : inscripciones) { Optional<Alumno> alumnoOpt = usuarios.stream() .filter(u -> u instanceof Alumno && u.getId() == insc.getAlumnoId()) .map(u -> (Alumno) u) .findFirst(); Optional<Curso> cursoOpt = cursos.stream() .filter(c -> c.getCodigo() == insc.getCursoCodigo()) .findFirst(); if (alumnoOpt.isPresent() && cursoOpt.isPresent()) { Alumno alumno = alumnoOpt.get(); Curso curso = cursoOpt.get(); insc.setAlumno(alumno); insc.setCurso(curso); alumno.inscribirseEnCurso(insc); curso.agregarInscripcion(insc); } } // 4. Reconstruir Calificaciones for (Calificacion cal : calificaciones) { Optional<Alumno> alumnoOpt = usuarios.stream() .filter(u -> u instanceof Alumno && u.getId() == cal.getAlumnoId()) .map(u -> (Alumno) u) .findFirst(); Optional<Curso> cursoOpt = cursos.stream() .filter(c -> c.getCodigo() == cal.getCursoCodigo()) .findFirst(); if (alumnoOpt.isPresent() && cursoOpt.isPresent()) { Alumno alumno = alumnoOpt.get(); Curso curso = cursoOpt.get(); cal.setAlumno(alumno); cal.setCurso(curso); alumno.agregarNota(cal); curso.addCalificacion(cal); } } }

¿Qué hace paso a paso?

  1. Limpiar listas:
    • Vacía todas las listas de relaciones en los objetos
    • Necesario porque al cargar desde JSON, estas listas están vacías
  2. Conectar Docentes con Cursos:
    • Cada curso tiene un ID de docente
    • Busca el objeto Docente real en memoria
    • Agrega el curso a la lista del docente
  3. Conectar Inscripciones:
    • Cada inscripción tiene alumnoId y cursoCodigo
    • Busca los objetos reales con Streams
    • Asigna las referencias en la inscripción
    • Agrega la inscripción al alumno y al curso
  4. Conectar Calificaciones:
    • Similar a inscripciones
    • Busca alumno y curso por IDs
    • Llama a alumno.agregarNota() que actualiza el promedio

🔗 Concepto: Reconstrucción del grafo de objetos

En JSON guardamos IDs. En memoria trabajamos con referencias. Esta función es el puente que convierte IDs en referencias, reconstruyendo todo el grafo de relaciones entre objetos.

✅ ¿Por qué es tan importante?

Sin esta función, los objetos estarían desconectados. Un alumno no sabría sus cursos, un curso no tendría inscriptos, etc. Esta función es lo que hace que el sistema funcione después de cargar datos.

🔍 Análisis

¿Qué es una interfaz?

  • Define un contrato: qué métodos debe tener una clase

public static Usuario validarLogin(String correo, String contrasena) { for (Usuario u : usuarios) { if (u.autenticar(correo, contrasena)) { // Usar el método de la interfaz return u; } } return null; }

Es una buena práctica programar contra interfaces en lugar de implementaciones concretas. Esto hace el código más flexible y testeable.

1. Herencia

Herencia

Jerarquías en el sistema:

Usuario (abstracta)

  • → Alumno
  • → Docente

Comparten: id, nombre, correo, contrasena, fechaRegistro, tipo

  • Polimorfismo: Podemos tratar a Alumno y Docente como Usuario en listas y métodos
  • Extensibilidad: Fácil agregar nuevos tipos (ej: Administrador extends Usuario)
  • Mantenimiento: Cambios en Usuario se propagan a todas las subclases

2. Polimorfismo

Polimorfismo

Ejemplos en el sistema:

Polimorfismo de subtipos (Usuario)
private static ArrayList<Usuario> usuarios = new ArrayList<>(); // Podemos agregar tanto Alumnos como Docentes usuarios.add(new Alumno(...)); usuarios.add(new Docente(...)); // Iterar sobre todos sin importar el tipo real for (Usuario u : usuarios) { System.out.println(u.getNombre()); // Método de Usuario }

La lista es de tipo Usuario, pero contiene objetos de diferentes subtipos. Esto es polimorfismo de inclusión.

Polimorfismo de métodos (Pago)
Pago pago; if (metodoPago == EFECTIVO) { pago = new Efectivo(...); } else if (metodoPago == TARJETA_CREDITO) { pago = new TarjetaCredito(...); } // El método correcto se ejecuta según el tipo real double monto = pago.calcularMontoFinal();

Aunque la variable es de tipo Pago, en runtime se ejecuta el método de la subclase correspondiente:

  • Efectivo.calcularMontoFinal() → descuento 10%
  • TarjetaDebito.calcularMontoFinal() → sin cambios
  • TarjetaCredito.calcularMontoFinal() → recargo 20%

Esto es dynamic dispatch o enlace dinámico.

Polimorfismo con instanceof y casting
public static List<Alumno> getAlumnos() { return usuarios.stream() .filter(u -> u instanceof Alumno) // Verificar tipo .map(u -> (Alumno) u) // Hacer casting .collect(Collectors.toList()); }

Usamos instanceof para verificar el tipo real en runtime antes de hacer casting. Esto es type checking dinámico.

3. Encapsulamiento

Encapsulamiento

Niveles de acceso usados:

private

Solo accesible dentro de la clase

private List<Inscripcion> historialCursos; private double promedio;

protected

Accesible en subclases

protected String nombre; protected int id;

public

Accesible desde cualquier lugar

public String getNombre() { ... } public void agregarNota(...) { ... }

static

Pertenece a la clase, no a instancias

private static ArrayList<Usuario> usuarios; public static void inicializarDatos() { ... }
🔍 Ejemplos de buen encapsulamiento

1. Promedio auto-calculado en Alumno:

private double promedio; // No hay setter público public void agregarNota(Calificacion nota) { this.notas.add(nota); actualizarPromedio(); // Actualización automática } private void actualizarPromedio() { // Lógica interna, nadie más necesita llamarla }

El promedio es privado y se calcula automáticamente. No se puede modificar directamente desde fuera.

2. Validación de cupos en Curso:

private List<Inscripcion> inscriptos; private int cuposMax; public void agregarInscripcion(Inscripcion insc) { if (inscriptos.size() < cuposMax) { inscriptos.add(insc); } }

La lista de inscriptos es privada. Solo se puede agregar a través del método que valida cupos.

4. Abstracción

Abstracción

Clases abstractas en el sistema:

Usuario (abstracta)

  • Define estructura común
  • Implementa autenticar()
  • No tiene sentido instanciar un "Usuario" genérico
  • Obliga a heredar (Alumno/Docente)

Pago (abstracta)

  • Define atributos comunes
  • Método abstracto: calcularMontoFinal()
  • Cada subclase lo implementa diferente
  • Template Method pattern
🔍 Abstracción vs Interfaz

Clase Abstracta

  • Puede tener atributos
  • Puede tener métodos implementados
  • Puede tener constructores
  • Herencia simple (extends una sola)

Interfaz

  • Solo constantes (static final)
  • Solo firmas de métodos
  • No tiene constructores
  • Herencia múltiple (implements varias)

5. Composición y Agregación

Relaciones entre objetos

Relaciones en el sistema:

Composición (fuerte)

El objeto contenido NO puede existir sin el contenedor.

public class Alumno { private List<Inscripcion> historialCursos = new ArrayList<>(); private List<Calificacion> notas = new ArrayList<>(); }

Las listas se crean en el constructor. Si se destruye el Alumno, las listas también se destruyen. Esto es composición.

Agregación (débil)

El objeto contenido PUEDE existir independientemente.

public class Curso { private Docente docente; // Referencia a Docente existente } // El Docente existe independientemente del Curso Docente doc = new Docente(...); Curso curso = new Curso(..., doc, ...);

El Curso tiene una referencia al Docente, pero el Docente puede existir sin el Curso. Esto es agregación.

Asociación bidireccional

Dos objetos se referencian mutuamente.

// Alumno conoce a Inscripcion public class Alumno { private List<Inscripcion> historialCursos; } // Inscripcion conoce a Alumno public class Inscripcion { private Alumno alumno; } // Se mantienen sincronizadas alumno.inscribirseEnCurso(inscripcion); // Agrega a historialCursos inscripcion.setAlumno(alumno); // Asigna referencia

Estas relaciones bidireccionales deben mantenerse sincronizadas manualmente. Es responsabilidad del programador.

💾 Sistema de Persistencia

Arquitectura de Persistencia

El sistema usa archivos JSON planos para persistir datos. Cada entidad tiene su propio archivo.

📄 usuarios.json

Alumnos y Docentes

{"id":"1234","tipo":"alumno",...} {"id":"5678","tipo":"docente",...}

📄 cursos.json

Cursos con docenteId

{"codigo":1234,"nombre":"POO",...} {"codigo":5678,"nombre":"BD",...}

📄 inscripciones.json

Inscripciones con IDs

{"idInscripcion":12345,...} {"idInscripcion":67890,...}

📄 calificaciones.json

Notas con alumnoId y cursoCodigo

{"alumnoId":1234,"cursoCodigo":5678,...}
🔄 Ciclo de vida de los datos
  1. Inicio de la aplicación:
    • GestorArchivos.inicializarDatos()
    • Lee los 4 archivos JSON
    • Parsea manualmente con regex
    • Crea objetos en memoria
    • Llama a reconstruirRelaciones()
  2. Durante la ejecución:
    • Todos los datos están en memoria (listas static)
    • Las operaciones trabajan con objetos
    • Navegación rápida por referencias
  3. Al guardar datos:
    • Se llama a addUsuario(), addCurso(), etc.
    • Se agrega a la lista en memoria
    • Se guarda TODO el archivo JSON de nuevo
    • Se sobrescribe el archivo completo
  4. Al cerrar la aplicación:
    • Los datos ya están guardados en JSON
    • No hay proceso de "cierre" especial
    • Los datos persisten para la próxima ejecución
⚠️ Problemas y limitaciones

1. Sin transacciones

Si la aplicación se cierra durante una escritura, el archivo puede quedar corrupto.

2. Sobrescritura completa

Cada guardado reescribe TODO el archivo. Ineficiente con muchos datos.

3. Parseo manual

Usar regex es propenso a errores. No maneja casos edge (comillas en strings, etc.).

4. Sin validación de integridad

No verifica que los IDs referenciados existan. Puede haber referencias rotas.

5. Todo en memoria

Con miles de usuarios, la aplicación consumiría mucha RAM.

✅ Mejoras sugeridas
  1. Usar librería JSON: Gson o Jackson para serialización automática
  2. Base de datos: SQLite o H2 para persistencia real
  3. Escritura incremental: Solo guardar lo que cambió
  4. Backup automático: Antes de sobrescribir, hacer copia
  5. Validación de integridad: Verificar referencias al cargar
  6. Lazy loading: No cargar todo en memoria al inicio

Estrategia de Serialización

El sistema usa una estrategia de serialización por IDs para evitar referencias circulares.

🔍 Problema: Referencias circulares
// Alumno → Inscripcion → Curso → Docente → Curso → ... Alumno alumno; alumno.historialCursos → Inscripcion inscripcion.curso → Curso curso.docente → Docente docente.cursosDictados → Curso (ciclo!)

Si intentamos serializar el grafo completo, entraríamos en un ciclo infinito.

✅ Solución: Guardar solo IDs

En memoria (runtime):

Inscripcion { alumno: Alumno (referencia) curso: Curso (referencia) }

En JSON (persistencia):

{ "alumnoId": 1234, "cursoCodigo": 5678 }

Al cargar:

  1. Se leen los IDs desde JSON
  2. Se crean objetos con referencias null
  3. reconstruirRelaciones() busca los objetos por ID
  4. Se asignan las referencias reales
